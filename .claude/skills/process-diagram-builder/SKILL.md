# Process Diagram Builder

Builds process/framework diagrams — ordered steps, fan-outs, branches, dependencies — as real computed geometry (SVG paths between measured DOM anchors), never a fixed-aspect SVG asset stretched to fit. Shares `components/ProcessConnector.tsx` as the underlying single-segment path primitive; a diagram composes multiple `"straight"` segments into trapezoid/branch shapes itself.

**Scope — explicitly excludes system maps.** `CmdbSystemMap`/`SoftwareSystemMap` are a different category (organic, hub-and-spoke "mental maps," not process-ordered) and are never touched or built from by this skill.

Reference implementation: `components/case-studies/data-health-monitor/DataCertificationTriggers.tsx` + its `.module.css`. Read both before building a new diagram — they're the working example every rule below was extracted from.

## Never do this

- **Never reason about layout from a CSS class's coded value — verify what it actually renders at first.** A shared card class's declared `width` (or any other coded value) is only a *starting assumption*, not ground truth, once flex-shrink, wrapping, or any other dynamic layout behavior can be in play — which is the default for every flex row in this diagram system. If an alignment/sizing bug doesn't resolve after a fix, or resolves and then recurs in a new form, **stop adding another computed layer on top and re-verify the foundational assumption instead** (what does this actually render at — ask the user, or measure it with `getBoundingClientRect()`). This happened for real, three times in sequence in one session, each fix papering over the same wrong assumption (`.stepCard` renders at its coded 301px) instead of questioning it: a computed gap formula, a CSS `calc()` offset, and a `flex-shrink: 0` fix all got layered on before the actual fix — measuring an already-reliable element's real rendered width in JS and reusing that number directly — was reached. When the user says a value renders differently than the code claims (e.g. "the trigger cards are around 181, not 301"), that is the real number — treat it as the fix's starting point, not as something to re-derive mathematically from the stylesheet.
- **Never derive a diagonal's angle from wherever the anchors happen to sit.** Every diagonal leg in a diagram uses one fixed angle (confirmed per-diagram, 30° in the reference implementation) — store it once (`LEG_ANGLE_DEG` + its `tan`/`sin`), reuse everywhere.
- **Never let ProcessConnector's own `gap` prop handle a joint between two of the diagram's own segments.** It recedes both ends symmetrically, which pulls two segments meant to touch exactly apart from each other. Pass `gap: 0` at every synthetic joint and pre-compute the exact shared coordinate instead.
- **Never treat an along-line gap as if it were the real visible vertical clearance.** A line at a non-right angle only drops `sin(angle)` px of real height per 1px traveled — convert any confirmed "real clearance" value via `clearance / sin(angle)` before using it as an along-line inset.
- **Never infer a branch's direction (which way it should point) by comparing measured anchor x-positions.** Real card/label widths can flip which side is "further out," silently reversing the branch. Pass direction explicitly.
- **Never anchor a horizontal lead-out to the whole card.** Anchor to the title label's own edge — the card's body text sits below the title and a card-edge anchor will visually cross it.
- **Never assume CSS already provides the vertical space a diagram's geometry needs.** If the diagram counts on two separate confirmed gaps stacking (e.g. "32px label→line, then 32px line→cards"), explicitly check the CSS actually provides their sum — a geometry that assumes more room than CSS gives collapses silently (legs shrink to zero length) rather than erroring.
- **Never center a group on an odd-numbered column span and rely on `justify-self: center` alone.** An odd span's own true center lands on a half-column line, which integer-grid centering can't hit — this produces a connector that reads as subtly angled instead of straight. Use an even-numbered span (e.g. center 6 of 12 columns) whose center lands on an integer line.
- **Never assume two elements share an X just because both are "centered."** `justify-self: center` (or flex `justify-content: center`) only centers within whatever span/container that specific element is centered in — not within the diagram's overall column. A fork outcome that's one member of an asymmetric flex pair (e.g. a bare "Yes" label next to a 301px "No" card, centered as a *pair* within the main column) has its own true center offset from that pair's shared center, which is itself offset from the full column's center. Continuing a sub-chain from that one outcome and centering the next element on the *full column* (`justify-self: center` on the same 4/10 span everything else uses) silently reconnects it to the wrong X, angling the connector.
- **Never assume a fork outcome's own ref gives the right center just because it's on "the same element the fork uses."** If the outcome's ref sits on a fixed-width wrapping box (e.g. `.forkLabel`, 301px, text centered inside it) but the continuation's own ref goes on a bare, auto-width text node, the two "centers" are computed from different box widths and a connector between them is still off — just less obviously than the full-column case above. Whatever structure (wrapping box + ref placement) the original outcome used, the continuation's own anchor needs the identical structure, not just a visually similar one.
- **Never assume CSS row-stacking gives a continuation the right Y when it continues from the *shorter* member of a row-sharing pair.** A row's own track height is always the *tallest* sibling's height — if the continuation's real source (e.g. "Yes") is shorter than the sibling it shares a row with (e.g. "No," with a title+body), the next row still starts after the full (taller) track height, not a confirmed distance below the real source's own shorter content. Forcing the shorter sibling to stretch to the row's height "fixes" the distance but detaches the connector from where the source visually ends, floating it below empty space instead of touching the real content. **When a continuation's real source is the shorter member of a differently-sized pair, position it from that source's own real measured anchor via a synthetic point (`CONNECTOR_LENGTH + CARD_GAP` past it, single inset since only one end is real) — the same technique `buildLeadConnector` already uses for a fan's own lead-in — not CSS grid/row stacking.** This is a JS-positioned exception to "prefer CSS" specifically because the real source's own natural position (not a container it shares with something taller) is what the continuation must measure from, and CSS grid has no way to express "distance from this one sibling's own content, ignoring the other."
- **Never stretch/fill siblings to force equal width when their content differs.** That makes width a function of the container, not the content. If equal width is wanted, measure each sibling's natural (unconstrained) width in JS and apply the max to all of them.
- **Never derive a fan's shoulder X from its own targets' midpoint.** `(outerLeft.x + outerRight.x) / 2` only matches the real external point feeding the fan (a label, the previous step) when the targets are symmetric/equal-width — true for 3 equal trigger cards, false for an asymmetric fork (e.g. a bare "Yes" label next to a 301px "No" card). A mismatched shoulder X angles the lead-in connector and skews the whole shape. Always pass the external point's own X in explicitly as the fan's `centerX` rather than deriving it — see Shape vocabulary.
- **Never derive one row's horizontal center from another row's content widths via a CSS `calc()` offset.** Two rows that are each independently centered within the same grid-column span don't share an X unless their content is symmetric — a row continuing from one member of an asymmetric pair (e.g. outcomes continuing from "Yes," the left member of a centered Yes/No pair) needs a real **measured** shift (JS, comparing the row's own natural center to the real feeding point's position), not a `calc()` expression assuming the two rows' geometry lines up. This happened for real: a `calc(-1 * (301px + gap) / 2)` offset, derived from the believed symmetry of the previous row's pair, left a visible kink where a fan's shoulder met its own mid-target — the real measured values didn't match the theoretical derivation closely enough. The fix was a `useLayoutEffect` that measures both centers directly and sets the shift as state.
- **Never let a step share a CSS grid row with a pain/branch card whose height isn't controlled.** Any row a main-chain step sits in determines the real CSS gap to whatever comes next via that row's full height (not the step's own content height) — a taller sibling in the same row silently inflates (or, if it sits *between* two chain elements, invents) the gap, producing a connector much longer than its confirmed length. This happened twice in the reference implementation, in both directions: once because a step shared a row with a taller unrelated pain card below it, once because a pain card occupied its own row sitting *between* two chain elements above it. The fix both times was giving the step (or moving the pain card into) the row immediately adjacent to its neighbor, sharing only with a pain card that belongs to the *same* step (see "Row-sharing pattern" below) — never with one that belongs to a different step or a different section of the diagram.
- **Never give diagram CSS classes content-specific names if the diagram system is meant to be reused.** Step-card classes (`.flowStep`, `.flowStep2`, `.flowStep3`...) stay generic/numbered on purpose — a future diagram copies the same agnostic classes rather than classes named after this diagram's own steps (`.ownerReviewsEachAssetStep` etc.), which would mean nothing to a different process. Content lives in the `CardContent` data, not the class name.
- **Never apply the simple-stub margin formula to a fan lead-in's CSS gap, or vice versa — they're different totals even though both sit on top of the same `.wrap` row-gap.** A simple step-to-step stub (both ends real anchors, e.g. `.flowStep2`) needs `CONNECTOR_LENGTH + CARD_GAP × ends`, and since `.wrap`'s row-gap already contributes to that total, the margin itself is that sum **minus** the row-gap. A fan lead-in (one real anchor → synthetic shoulder → `BRANCH_HEIGHT` → targets, e.g. `.triggersLabel`/`.decisionLabel`/`.doubleCheckAnswers`) needs `CONNECTOR_LENGTH + CARD_GAP` with **no row-gap subtraction** — the row-gap is extra headroom on top, not part of the budget, because `BRANCH_HEIGHT` still has to fit inside the total. Copying one formula for the other either collapses the lead-in's visible length (margin too short) or inflates a simple stub's (margin too long) — this happened for real, building the Match/Don't Match fork's lead-in with the simple-stub formula instead. Check which of the two cases a new connector actually is before picking a formula, not which existing class looks similar.
- **Never leave a fixed, ref-independent constant (gap/length/angle) declared inside the measuring `useLayoutEffect`.** `CARD_GAP`, `BRANCH_HEIGHT`, `CONNECTOR_LENGTH`, `LEG_ANGLE_DEG` and anything derived purely from them (`LEG_TAN`, `CARD_GAP_ALONG_LINE`) belong at module scope, declared once, next to each other — not re-declared inside the effect every time it runs. Anchors (`const xTop = anchor(...)`) are the only things that belong inside the effect, since they depend on refs; keep all of them grouped together in one block, not scattered next to whichever shape's code happens to need them.

## Naming shapes

- **Fan / fork** — the same shape, `buildFanTrapezoid`, used interchangeably: one point connected to 2+ targets via a shared horizontal shoulder bar + fixed-angle diagonal legs. Say "fan" for multiple instances of the same thing (Triggers → 3 trigger cards); say "fork" for categorical choices (Yes/No, Correct/Wrong/No Longer Exists). Never a different function or shape for one vs. the other.
- **Merge** — the *same* fan shape, read in reverse: multiple real sources converging into one point instead of one point spreading into multiple targets. Still `buildFanTrapezoid`; the only difference is which end is conceptually "the input."
- **Upward vs. downward fan** — the `direction: "down" | "up"` param, describing which side the shoulder sits on relative to the targets, not which way information flows: `"down"` = shoulder above the targets, legs point down to them; `"up"` = shoulder below the targets, legs point up to them (e.g. a merge feeding a card further down).
- **Branch** (`buildBranch`) — one source to one target, no shoulder, just a horizontal lead that bends into the diagonal. Branches never flip vertically (always top-down, per the Anchor rule) — their mirrored axis is `direction: 1 | -1`, left vs. right, i.e. which way the lead grows outward before bending.
- **Loop** (`ProcessConnector shape="halfCircle"`) — the one true arc shape; `bulge: "left" | "right"` for which side it curves toward.

## Shape vocabulary

- **N-way fan-out/fork from one point** (e.g. a label feeding 2+ cards — a 3-way trigger fan and a 2-way Yes/No fork are the *same* shape, `buildFanTrapezoid`): one shared horizontal **shoulder line**, a diagonal leg from each outer end down to the real outermost targets, plus a straight vertical **center stub** through the shoulder to any target sitting strictly between the two outer ones (a no-op loop when there are only 2 targets — nothing extra needed for a fork). The shoulder's Y is derived purely from the real targets and a confirmed `height` (how far the shoulder sits from the target row). The shoulder's X (`centerX`) is **always passed in explicitly** as the real external point's own X (the label/step feeding the fan) — never derived from the targets' own midpoint (see Never-do-this). The function itself builds *only* this shape; it has no opinion about, and builds no segment toward, whatever feeds into it from outside — that's the separate self-standing lead-in/out connector below.
  - **Scales to any target count.** The two diagonal legs always keep their fixed-angle offset (`dx = height / tan(angle)`) from the outer targets — that's the confirmed shape and never changes with target count or spacing. But the horizontal bar's own *drawn extent* is not simply `shoulderLeft`→`shoulderRight` — with more targets packed closer together than `dx`, a mid target can sit further left/right than those two points, leaving its stub floating outside the bar. The bar's endpoints are `Math.min`/`Math.max` across the two legs' anchors *and every mid target's x*, so the bar always reaches however many connections exist while the legs' fixed angle never moves.
  - **Two-color split**: pass `color` as `{ left, right }` instead of a single string to color each half of the shoulder bar, and the leg/mid-stub on that half's side, independently — split exactly at the shoulder's center. Used for a fork whose outcomes read differently (e.g. a Yes/No fork where the failure side is warning-red).
  - **Which target becomes a diagonal leg vs. the straight mid-stub is decided by real sorted x among *all* targets passed in — never assume based on intent/labeling.** Adding a target to an existing fan can silently change another target's role: a target you think of as "the middle one" conceptually can end up as an outer diagonal leg if a *different* target (e.g. one from a different row, positioned further out) sorts further from center. This happened for real: a 3-way merge was assumed to put the two same-row targets on the outer legs and the new (different-row) target on the mid-stub, but the new target's real x was actually the furthest out, making it an outer leg instead — the roles only became clear after checking the real measured x values, not from how the targets were described.
  - **Reconnecting a leg's own tip later:** a target can be a synthetic "hanging" point (not tied to a real DOM anchor) that gets a real connector attached to it afterward. When that new connector needs to be perfectly straight (e.g. a vertical drop sharing the hanging point's exact x), connect to the **raw hanging-point coordinate**, not the leg's own diagonally-inset tip — chasing the leg's exact (diagonally-inset) endpoint pulls the new connector slightly off its own straight axis, since that inset moves along the diagonal's slope, not purely toward the hanging point. A small, accepted gap between the two segments' real drawn ends reads better than a line that's subtly not straight. Leave the leg's own length alone (same `height` as every other leg in the fan) rather than growing it to compensate.
- **Self-standing lead-in/out connector**: a single straight segment between one real external point (a label, a step) and a fan's own `shoulderCenter` (returned by `buildFanTrapezoid`). Always build this *separately* from the fan, never inside it — see Never-do-this for why collapsing them together breaks.
- **Simple step-to-step connector**: a single straight segment between two real, already-built step anchors (no fan, no bend) — both ends get the shared gap inset. This is the common case for consecutive main-chain steps; a tiny `buildStepConnector(from, to)` helper covering exactly this (return `[]` if either anchor is null, so it's safe to spread unconditionally) is the reusable shape here, not a bespoke segment per pair of steps.
- **Single branch, no shared junction — the standard shape for every pain branch in this diagram.** One pain card to its own parent step card: a horizontal **lead** growing outward from the step's title label, bending into the fixed-angle diagonal, with the diagonal's horizontal run derived from the *entire* real vertical gap (`/ tan(angle)`) and the lead absorbing whatever's left over. `bottom` is the pain card's own real top-center (`anchor(ref, "top")`, per the Anchor rule's vertical-approach convention, never a label anchor) — the connector actually touches the real card (inset `CARD_GAP_ALONG_LINE`), it doesn't stop short.
  **The card's position is the independent variable, and it's a pure {x, y} margin pair, not derived from the connector.** `STEP_PAIN_GAP` (horizontal) and `STEP_PAIN_VERTICAL_GAP` (vertical) are confirmed, shared, tunable distances: each pain card's own real edge sits exactly `STEP_PAIN_GAP` from its *parent step card's own real edge* (card-to-card, not label-to-label), and its own real top sits exactly `STEP_PAIN_VERTICAL_GAP` below that same step card's own top edge (not its bottom, and not its title — so a step card's own body-text length never changes the real gap). Both computed together in one dedicated `useLayoutEffect` (see `DataCertificationTriggers.tsx`'s `painBranches` config: one `{ key, stepCardRef, cardRef, direction }` entry per pain card) and applied as one `translate(x, y)`. This standardizes what used to be CSS row-sharing + `align-self: end` producing a different real vertical distance per card depending on sibling row heights. The connector is a fully separate, derived shape that auto-adjusts its lead/diagonal split to reach wherever these gap-derived positions and the step's own label height happen to put the card — it never sets the card's position itself.
  **Why this doesn't reintroduce the earlier "backwards 7" bug:** that distortion happened when a pain card's position was pinned to an *unrelated* target (another step entirely) that could end up too close to, or even behind, the label in the branch's own direction, making the full-run diagonal's horizontal need exceed the actual distance available and flip the lead backward. Deriving every pain card's position *outward* from its own parent step card's edge by a positive, confirmed gap guarantees the target is always further out than the label in the correct direction — so the lead's "leftover" distance can't go negative.
  Two earlier intermediate versions existed and were abandoned: (1) a short `BRANCH_HEIGHT`-capped diagonal intentionally stopping short of the card, with the card's position derived *from* the connector's endpoint, and (2) that card position aligned to an unrelated step (Implement Fix) instead of its own parent. Both were replaced once the real intent (a literal, controllable card-to-card gap, with the connector as the dependent/auto-adjusting part) was clarified — if a future session finds either of those patterns referenced elsewhere, they're superseded by this entry.
- **Half-circle loop connector** (`ProcessConnector`'s `shape="halfCircle"`): a true semicircular arc for a loop-back (e.g. a failure path returning to retry an earlier step) — this is the one shape that genuinely cannot be composed from straight segments, so it's a real new `ProcessConnector` prop, not hand-composed by the diagram. `from`/`to` must share the same X (a vertical diameter); radius is always derived as half the vertical span, never a separate prop; `bulge: "left" | "right"` picks which side it curves toward. Pair it with a straight horizontal lead-out segment (see reference implementation) to actually reconnect into the target step — treat the arc + its lead as **one shape**: same color, same `dashed` value, arrowhead only at the final reconnection point (not mid-arc). A label sitting at the arc's own center (its rightmost/leftmost bulge point, `radius` out from the diameter) needs its own JS-computed position (state, not a line), since it isn't a connector segment.
- Every non-half-circle shape above is composed from multiple `"straight"` `ProcessConnector` segments with manually computed endpoints in the diagram component itself — never a new prop on `ProcessConnector` for those.

## Anchor rule

- Vertical approach (line comes from directly above/below a card) → the card's own top/bottom-center.
- Horizontal lead-out (line grows sideways before bending down) → the **title label's own edge**, inset by the shared gap value, not the whole card.
- Aligning to a label's vertical middle (e.g. a loop connector reaching a step's level without touching it) → the anchor helper's `"center"` side, which returns the element's true center (x and y) directly — never anchor `top` and `bottom` separately and average them by hand at the call site.

## Gap model

One shared constant (e.g. `CARD_GAP`) means **real vertical clearance**, not along-line distance, across the entire diagram. Apply it:
- Directly, for vertical or horizontal segments (`sin(90°) = 1`, no conversion).
- Via `CARD_GAP / sin(angle)`, for any segment at the diagram's fixed diagonal angle.

Every segment that touches a real card/label gets this inset, computed manually (`gap: 0` passed to `ProcessConnector`, with the actual endpoint pre-shrunk toward the real anchor). Every segment that only touches another segment's own synthetic joint gets `gap: 0` and an exact, untouched coordinate.

A second confirmed constant, `CONNECTOR_LENGTH`, is the actual *rendered* length of every straight, non-fan, real-anchor-to-real-anchor stub (a simple step-to-step connector) — not a raw/pre-inset distance. `CARD_GAP` breathing room is added **on top** of it at each real end, so the real CSS space a stub needs is `CONNECTOR_LENGTH + CARD_GAP × (number of real ends it touches)`. A fan's own lead-in/out connector additionally needs `BRANCH_HEIGHT` (the fan's own confirmed shoulder-to-target distance) stacked on top of that sum, since the shoulder sits `BRANCH_HEIGHT` further back from the target row than the lead-in connector's own far end.

**When two separately-built segments must meet at one point, pick the authoritative one and make the other reach it — never let both compute their own "almost there" endpoint independently.** If one of the two segments has a hard constraint (e.g. it must stay purely vertical/horizontal), its endpoint is fixed and correct by definition; the other segment (e.g. a fan leg with its own `CARD_GAP` inset) should simply be **extended to that exact coordinate**, not recomputed via its own separate gap/angle math. Two independently-derived "close enough" endpoints are never guaranteed to coincide — that mismatch is what produces either a visible gap or an unwanted slight-off-axis tilt. Decide which segment is authoritative *first*, before writing either one's math.

## Downstream fixed-width gap

When a fan-out's own targets each continue into their own fixed-width downstream card, **reuse the same item width and gap token on both rows** rather than inventing a one-off narrower width for either, and rather than computing a custom gap from the downstream card's width. Matching widths/gaps on both rows means adjacent items are automatically the same distance apart on each row, so the downstream cards can't overlap — no extra math needed. Only the row's own horizontal *centering* needs a JS-measured shift (see above); the *spacing* takes care of itself once both rows share the same width.

**A coded width is not the same as a rendered width — measure it, don't assume it.** A shared card class's declared `width` (e.g. `.stepCard`'s 301px) only renders at that value if the row's content actually fits the available grid-column space. Once a row has enough items that the total exceeds that space, the browser's default `flex-shrink: 1` silently compresses every item below the coded width — so two rows that are supposed to "reuse the same width" can end up at *different* real widths (a 3-item row shrinks more than a 2-item row) even though both reference the identical CSS class, breaking the whole alignment relationship. This happened for real, twice: once as wrapped text (fixed with `flex-shrink: 0`), and again as misaligned/diagonal connectors even after adding `flex-shrink: 0` to one row's class but reusing a *different* coded-width assumption elsewhere. The robust fix: measure an already-reliable reference element's real `getBoundingClientRect().width` in JS (e.g. an existing trigger card that's known to visibly render smaller than its coded width) and apply that exact measured number, with `flex-shrink: 0`, to every row that needs to match it — never trust a class's declared width number to be what actually renders once shrink is in play.

## Row-sharing pattern

CSS Grid gives each step its own `grid-row`, but a lone step in its own row leaves the connector's required space unconfirmed by default — the established pattern (confirmed each time per Gap model) is:
- Each main-chain step shares its `grid-row` with the **previous step's own pain/branch card** (not a step from elsewhere in the diagram, and not an unrelated pain card), using `margin-top` on the step to push it down within that shared row by whatever's needed on top of `.wrap`'s row-gap to hit the confirmed total (see Gap model's `CONNECTOR_LENGTH` formula).
- A step's **own** pain/branch card then goes in the **next** row down, repeating the pattern for whatever comes after it.
- Never let a step and a pain/branch card share a row, or sit in sequential rows, unless they belong to the *same* link in the chain — see Never-do-this for what breaks otherwise.
- **Any row with two siblings of different heights needs `align-items: stretch`** (the default — don't override it to `flex-start`/`center` on a row whose shorter sibling continues onward). A flex/grid row's own track height is always the *tallest* sibling's height regardless of `align-items`; without stretch, a shorter sibling's own measured bottom stops at its own content height, leaving an uncontrolled, content-dependent gap between it and the row below before the confirmed `margin-top`/`CONNECTOR_LENGTH` space even starts. With stretch, every sibling's box — and so its measured anchor — always reaches the row's real bottom edge, regardless of how tall the other sibling's content happens to be. This doesn't change anything visually (plain block children still render their text at the top of a taller box), only what a `getBoundingClientRect()` anchor reports.

## Constants and naming

- Fixed, ref-independent constants (`CARD_GAP`, `CONNECTOR_LENGTH`, `STEP_PAIN_GAP`, `STEP_PAIN_VERTICAL_GAP`, `BRANCH_HEIGHT`, `LEG_ANGLE_DEG`, and anything derived purely from them like `LEG_TAN`/`CARD_GAP_ALONG_LINE`) live at module scope, grouped together, declared once — never re-declared inside the measuring `useLayoutEffect`.
- Anchors (`const xTop = anchor(...)`) are the only things computed inside the effect, since they depend on refs — keep all of them grouped in one block near the top of the effect, not scattered next to whichever shape's code happens to need one.
- Step-card CSS classes stay **generic/numbered** (`.flowStep`, `.flowStep2`, `.flowStep3`...), never content-named (`.ownerReviewsEachAssetStep`) — the diagram system is meant to be copied for future diagrams, and a generic class means something to a diagram that isn't this one. Content lives in the `CardContent` data (title/body strings), not the class name.

## Steps to build a diagram

1. Read `PLAN.md`'s "Process Diagram / Connector System" section and `DataCertificationTriggers.tsx`/`.module.css` first.
2. Identify which anchors are real DOM elements (cards, labels) vs. synthetic (shoulder points, bend points) — only synthetic points are "derived," never a real anchor's position.
3. Pick the diagram's fixed diagonal angle and confirm it with the user before writing code (this is a concrete design value, not an "obvious default").
4. Pick the shared gap/length constants' values (`CARD_GAP`, `CONNECTOR_LENGTH`, `BRANCH_HEIGHT`) and confirm each with the user.
5. Build anchors via `getBoundingClientRect()` in a `useLayoutEffect`, matching the Anchor rule above, grouped together per Constants and naming.
6. Compose each shape from `"straight"`/`"halfCircle"` `ProcessConnector` segments per the Shape vocabulary above, using generic class names per Constants and naming.
7. Check CSS provides the real vertical space the geometry assumes (see Never-do-this and Row-sharing pattern) — confirm any new CSS value (a `margin-top`/`margin-bottom` addition) with the user before writing it.
8. Update `components/built-components.md`'s `process-connector` entry and this skill file if a new shape pattern or rule gets confirmed.
